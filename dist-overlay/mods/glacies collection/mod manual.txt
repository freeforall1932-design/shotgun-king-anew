---------------------------------------------------------------------
   Floor Restarter
- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
   You can restart your current floor if you can afford a restart.
   The restart will fail if no `restart` and `temp_restart` stats can be payed.
   By default, you can restart by pressing `/~ key.
   This can be disabled in the settings.
   There are also other ways to make a restart.

restart = <int>
temp_restart = <int>
   Restarting a floor costs these two stats.

   Specifically, if you have a positive `temp_restart`,
   restarting will give yourself the effect `temp_restart=-1` until the next floor.
   If you don't have a positive `temp_restart` but have a positive `restart`,
   restarting will give yourself a permanent effect `restart=-1`.

special = "restart"
   In addition to the `/~ key, allows restarting by right clicking.

restart_ | _restart | _reset
   See below: Composite Effects.


---------------------------------------------------------------------
   Composite Effects
- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
   Composite effects are effects that will be triggered under certain circumstances.
   A composite effect consists of two or more parts, but the core is always: <trigger>_<command>.
   The structure of a composite effects are similar to a train:
   triggers are the head, commands are the tail, and an indefinite number of conditions are the carriages.
   
   Some triggers pass arguments to the attached conditions and commands.
   Some triggers or commands have associated enhancements,
   which do not have to be triggered or written in the <trigger>_<command> format as they are not composite effects themselves.

   Some notations and terminology:
      Things in brackets <> refer to an arbitrary member of that class.
      When writing effects, they should be replaced by what you need.
      e.g.: if you want to use hurt_<piece name>_, it should be like hurt_bishop_ etc.

      trigger: kinda like the prefix of a composite effect, e.g.: hurt_bishop_
      condition: the middle part of a composite effect, optional. e.g.: _if_p_flying_
      command: the suffix of a composite effect, e.g.: _hit

      effect: the name of a general effect found in cards, ranks etc.
         Not necessarily a customised or composite one.
         e.g.: firepower, queen_iron, hurt_bishop_if_p_flying_stun, ...
         In an effect such as firepower=1, 1 is called the value of this effect.
         In composite effects, the value will be used by the command.
         Usually, triggers and conditions do not care about the value.

      piece name: pawn, bishop, leader, all, etc.

      stack: this is where the game stores effects.
         The game collects effects from ranks, weapons and cards etc., and then form the stack.
         In this process, like effects are merged.
         e.g.: if you have two Rightful Curtsy, the stack will contain an effect knockback=100
         instead of two entries of knockback=50.
         And of course, effects in the stack lose track of which cards they come from.

      argument: an object (number/piece/card) that a command has access to.
         Many conditions and commands require arguments to work.
         Usually, arguments are provided by triggers and conditions.
         e.g.: command _stun stuns a piece, but it requires an argument to tell it which piece to stun.

         Arguments have a key and a value. Key is the name of this argument, and value is the actual object.
         e.g.: if you have an argument p, the key of this argument is "p", and the value might be some piece on the board.
         Arguments are accessed by their key, so it is important to make sure they are stored with the correct key.

      argument space: this is where the arguments are stored.
         The argument space of a command contains all the arguments it can access.
         When these conditions and commands are triggered, they seek arguments from here.
         Besides arguments passed by triggers and conditions,
         in each argument space there are also some built-in arguments that are accessible by default.

         Built-in arguments (in <key> = <value> form):
            - args = this argument space itself
            - stack = the stack
            
            - turn = turn number
            - floor = floor number
            - rank = rank number

            - hero = the black king piece
            - leader = the leader piece type (a number)
            - ammo = number of ammo
            - chamber = number of loaded shells
            - grenade = number of grenades
            - shield = number of folly shields
            - time = playing time
         
         e.g.:
            _if_args_p_ = if there is an argument p in the argument space
            period_1_if_args_p_ammo=1 doesn't do anything.
            period_1_ifHero_if_args_p_ammo=1 works like period_1_ifHero_ammo=1.

            _if_stack_blade_ = if you have blade
            _if_stack_<effect>_ is very similar to _ifHas_, except that _if_stack_<effect> also stores the value of <effect>.
            In the above example, it will store your blade stat as argument "blade".

            consider:
            greneff_grenadeHit = 1
            bundle_grenadeHit = {"if_args_firerange_inc_firepower","if_args_firerange_halt",
            "if_args_firepower_if_stack_firerange_ifHas_N_ammo","if_stack_firepower_ifHas_N_ammo"}
            This effect gives you 1 firepower each time your grenade hits at least three pieces.
            (firepower and firerange are used as a marker simply because they always exist in stack,
            similarly ammo is just a random placeholder since it never gets triggered anyways)

         Sometimes multiple commands are triggered in series (in the case of forAll and bundles).
         If we view them as a tree, then a trigger is the root, the commands it triggers are the branches.
         Triggering multiple commands corresponds to having multiple branches. Branches can lead to more branches.
         All commands originating from the same root share the same argument space.
         More details in Bundle Command Notes #3.

      event: some commands are not executed upon being triggered. Instead, they register an event.
         These commands are tagged as "EVENT".
         All events will be held in a queue, and will be played one by one just before you are able to play.
         Event commands will be executed when the event is played.

      experimental: entries tagged as "EXPERIMENTAL" are very unstable.
         These entries are more likely to cause bugs so they should be used with care.

   Warning:
      Effect chaining can result in bugs.
      For example, killing a piece while it's still moving might cause a softlock.

-- Bundle Commands --

bundle_<com> = {<com1>,<com2>,...}
   Defines a command _<com> that is equivalent to a sequence of commands.

   When _<com> = {<val1>,<val2>,...} is triggered,
   it will trigger _<com1> = <val1>, then _<com2> = <val2>, ... etc.

   Alternatively, when _<com> = <val> is triggered,
   it will trigger _<com1> = <val>, then _<com2> = <val>, ... etc.

Caveat:
bundle_<com> is an effect itself, so it can be written on a card.
But when the card is flipped, you immediately lose all effects on that card, including bundle_<com>,
which makes the bundle command undefined.
So it is recommended to put it in script.lua, making it a globally applying effect.
Alternatively, they can be put in "base" of gamemode files,
but the bundle command will only be defined within that gamemode, since you only have the effect bundle_<com> there.

Example:
bundle_replenish = {"ammo","boost_firepower"}
   This effect defines the command _replenish.

   Then we can craft things like:
   period_1_replenish = {1,1} - on every turn, gains 1 ammo and +1 firepower for the next shot.

   Note that this is equivalent to period_1_replenish = 1 because {1,1} consists of the same value.

   When writing descriptions, we can put
   effect_period_1_replenish::on every turn, gains $0 ammo and +$1 firepower for the next shot.
   The number of placeholders ($0,$1,...) is not limited, but all values are inserted without the +/- sign.

Reasons for using bundle commands: [be familar with Conditions before reading this]

   1. To make sure commands are triggered in the correct order.

      Imagine we want +1 max hp and +1 hp for all kings on every turn.
      This can't be done by period_1_inc_king_hp=1 & period_1_forAll_king_heal=1
      since commands are triggered in a random order.
      There's a chance that _forAll_king_heal=1 is triggered first, but kings with full hp won't get healed.
      After _inc_king_hp=1 is triggered, they end up having an empty heart.

      But if we define bundle_incHP = {"inc_king_hp","forAll_king_heal"},
      then period_1_incHP=1 will always give one full heart to kings.

   2. To make commands closely binded.

      Imagine we want, on each turn, a 50% chance of gaining 1 ammo and +1 firepower for the next shot.
      This can't be done by period_1_rnd_50_boost_firepower=1 & period_1_rnd_50_ammo=1
      since this is not looking at the same coin; this is tossing two independant coins.
      That means we might get just +1 firepower but no ammo.
      
      But if we define _replenish as in the example above, then period_1_rnd_50_replenish=1 does what we want.
      _ammo and _boost_firepower are binded together, so that we always get both of them, or neither.

   3. To make sure commands share the same argument space.

      Imagine we want to deal 1 damage to and frighten a random piece on every turn.
      This can't be done by period_1_ifExist_all_hit=1 & period_1_ifExist_all_frighten=1
      since it's totally possible that we end up hitting piece A but frightening piece B.

      But if we define bundle_hitAndFrighten = {"hit","frighten"},
      then period_1_ifExist_all_hitAndFrighten=1 will always target the same piece.
      This is because _hit and _frighten are activated by the same trigger period_1_ifExist_all_,
      so they share the same argument p that is randomly chosen by _ifExist_all_.

      This becomes even more important when considering _halt.
      Imagine we want, on each turn, a 50/50 chance of gaining +1 firepower/-15 spread for the next shot.
      This can't be done by period_1_rnd_50_boost_firepower=1 & period_1_rnd_50_boost_spread=-15
      for the same reason as #2.

      But we can define:
      bundle_head = {"boost_firepower","halt"}, bundle_coinToss = {"rnd_50_head","boost_spread"},
      then the effect can be achieved by period_1_coinToss = {{1,1},-15}.
      (Note that {{1,1},-15} can be simplified to {1,-15})
      See that there is a 50% chance of gaining firepower, and then _halt will shut down the rest of the process.
      If we don't get the firepower, _halt will not be triggered, then we end up getting -15 spread.

   4. To be more concise and efficient

      Imagine we want an effect similar to the wand of downpour that activates on each turn.
      That is: deal a total of 8 damage to random enemies on each turn.
      This could've been done by:
      period_1_ifExist_all_hit=1, period_1_ifExist_all_rnd_100_hit=1, period_1_ifExist_all_rnd_101_hit=1, ... repeated 8 times.
      But this makes an ugly solution.

      Instead we can define: bundle_eightHits = {"ifExist_all_hit","ifExist_all_hit","ifExist_all_hit",
      "ifExist_all_hit","ifExist_all_hit","ifExist_all_hit","ifExist_all_hit","ifExist_all_hit"}.
      Note that we don't have to add the rnd part to make them different from each other.
      Then when we make the card, we just need a simple period_1_eightHits=1.

   5. Even more efficient by use of recursion

      Imagine we want the following effect:
      when this card is clicked, drain and turn the total hp of all pawns on the board into firepower for the next shot.

      This could've been done by repeatedly putting instances of
      click_ifExist_pawn_boost_firepower=1 & click_ifExist_pawn_hit=1.
      Basically, if there is a pawn on the board, we get +1 firepower and deal 1 damage to it,
      then repeat this process suffciently many times so that no pawn can survive.
      But we wouldn't know how many times of repetition counts as "suffcient",
      and it will surely be a mess to write down the effects.

      But if define bundle_bloodlust = {"ifExist_pawn_boost_firepower","ifExist_pawn_hit","ifExist_pawn_bloodlust"},
      then one simple click_bloodlust = 1 will do.
      See that _bloodlust endlessly repeats itself until no pawn is present on the board.

   Conditions & Controls (Optional, Stackable)
   
   Conditions decide whether the attached command should be executed.
   If they are not passed, the stop the process.
   Some of the entries are controls instead of conditions. They allow composite effects to be even more customisable. 
   For example, they can be used to make commands fork, or allow you to select a piece to apply the command.

   When combined with triggers/commands, the whole thing can be seen as a trigger/command.
   e.g.: _if_p_flying_hit can be thought of as a command.

_not_
   Negates THE FOLLOWING condition.

_if_<arg>_<key>_
   Requires argument <arg>:
   If argument <arg> has an attribute named <key> and the value of this attribute is not "false"
   >>> If true, passes the value as argument <key>

   *When writing this condition, replace any _ in <arg> and <key> with UNDER

   Examples:
   move_king_not_if_p_bad_ammo=1: +1 ammo each time you move
   move_bishop_if_p_flying_ammo=1: +1 ammo each time a flying bishop moves
   move_pawn_if_p_sq_ammo=1: +1 ammo each time a pawn moves if it's occupying a square

   The one above is trivially true, but the next one might be tricky:
   move_pawn_if_p_sq_if_sq_moat_ammo=1: +1 ammo each time a pawn moves to a moat
   Here we use if_p_sq not for checking anything, but for generating the argument sq from the attributes of p.

   Adding more stuff:
   move_king_if_p_sq_if_sq_moat_not_if_p_bad_ammo=1: +1 ammo each time you move to a moat
   move_king_if_p_wsq_if_wsq_moat_not_if_p_bad_ammo=1: +1 ammo each time you move from a moat
   move_all_if_p_bad_promote=1: pieces promote after moving

   Advanced examples:

   hurt_all_retrostrike={-1,{1,1}}, death_all_if_p_hurt_retrostrike={-1,{1,1}}:
   [Bundle Command _retrostrike as defined in the settings]
   Each time a piece is damaged:
   - if it has moved from a square, strike the piece that's currently occupying that square with lightning
   - if no lightning is summoned in the first step, lose 1 firerange until your next shot

   Other examples:
   click_not_if_ca_flipped_ammo=1: +1 ammo each time you click this card (disabled if flipped)

_setValue_<int/key>
   Sets the value of this command as <int>/argument <key>
   *For <key>, replace spaces with SPACE, and replace _ with UNDER.

   e.g.:
   period_1_setValue_2_ammo=1 is the same as period_1_ammo=2.
   period_1_if_stack_ammoUNDERregen_setValue_ammoUNDERregen_ammo=1
   gives you as many ammo as your ammo_regen on each turn.

   Only affects its own command. Doesn't change any other command.
   e.g.:
   bundle_example = {"ammo","setValue_2_ammo","ammo"}
   then _example=1 gives you a total of 4 ammo instead of 5.
