# Review — pre-live-test readiness check (2026-10-03, session 2)

> Requested because the README was ambiguous (does the tooling *patch the game*
> or *build a clone*?) and confidence before the first live test was low.
> This review states what is mechanically verified, what is unverified, what
> was found broken, and the recommended test order.
> Companion docs: `HANDOFF.md` (state), `WORKLIST.md` (tasks).

## 1. The question the README failed to answer

| Tool | What it actually does | Target | Undo |
|---|---|---|---|
| `build-dist.ps1` | **Copies the whole game** → `dist/ShotgunKing-Modded/`, then adds `mods/` inside the copy | the copy | delete `dist/` |
| `apply.ps1` | copies **only** `modded/sk-rework/` into a game folder's `mods/` | your real install (adds one folder) | delete `<game>/mods/sk-rework` |
| `install-mods.ps1` | unpacks workshop zips into `mods/` | your real install (adds folders) | delete those folders |
| `make_100pct_save.py` | writes `save/*.sav` in the folder you point it at (auto-backup) | whichever folder you pass | `--restore` |

**No tool edits, patches, repacks or replaces `shotgun_king.exe` or
`data.sgr`.** "Injection" in this repo only ever means *adding folders under
`mods/`* — a feature the game itself supports. This is now stated at the top
of the README.

## 3. Findings

**F1 — README quick-start unlocked the wrong save (doc bug, medium).**
Old order: build copy → unlock *original install's* save → play the copy.
The copy is a snapshot, so it kept the **old** save; the player would see no
unlocks. README now unlocks *after* building, pointing at
`dist\ShotgunKing-Modded` (or before building, pointed at the original, if
the same save should live in both). *Fixed.*

**F2 — `make_100pct_save.py` could lose the whole `throne` table (latent bug).**
`throne = prog.get("throne", {})` modified a throwaway dict when the key was
absent, then saved `prog` without it. Switched to `setdefault`. *Fixed.*
(Would only trigger on a save that has no `throne` key at all.)

**F3 — ugly tracebacks instead of instructions when saves are missing (low).**
Running the tool before the game has ever launched → `FileNotFoundError`.
Now: "launch the game once so it creates its saves, then re-run". Also
`--restore` now works even if `save/` was deleted. *Fixed.*

**F4 — `save_codec.py --help` crashed (cosmetic).** Treated `--help` as a
filename. *Fixed.*

**F5 — `build-dist.ps1` stray-archive scan (low, static-parse finding).**
`Get-ChildItem -LiteralPath … -Include *.rar,*.zip -Recurse` is a known
PowerShell grey zone (`-Include` is unreliable with `-LiteralPath`), and the
tree-sitter parse flagged the unquoted wildcard list. Replaced with an
unambiguous `Where-Object { $_.Extension -in '.rar','.zip' }`. Also fixed a
typo in the generated `PLAY-THIS.txt` (`game''s`). *Fixed.*

**F6 — status language overclaimed (doc, medium).** README said features were
"✅ shipped" when the honest status is "code exists, never run on a real
game". Rewritten as three states: ✅ verified in sandbox · 🟡 code ready,
unproven in game · ⛔ blocked pending `log.txt`.

**F7 — the built copy inherits whatever is in the original `mods/` folder
(informational).** Because the build copies the game folder as-is, half-broken
extracted mods from earlier experiments come along for the ride. Archives are
cleaned, extracted leftovers are not. If the first launch misbehaves, the
quickest isolation is to temporarily rename `<game>/mods` and rebuild, or ask
for a `-NoInheritMods` switch (one-line change in `build-dist.ps1`).

**F8 — docs reference `uploads/` and pack files as if they were in the repo
(informational).** They are gitignored by design and exist only on the owner's
machine. Notes that read "see uploads/…" are provenance notes, not paths in a
fresh clone. Kept, but flagged at the top of README's layout section.

**F9 — HANDOFF.md pointed at the previous session's branch name
(`arena/01a10145-…`) and PR #1 status (informational).** PR #1 is merged;
branch corrected. *Fixed.*

## 4. Risks that remain (can't be removed from here)

1. **PowerShell never executed anywhere.** Syntax parses clean, but first run
   on Windows may still surface behaviour quirks. Mitigation: every script is
   preceded by a no-write dry run (`-List`) or an isolated target (`dist/`).
2. **Save semantics.** The byte format is proven; whether v1.623b *accepts*
   an edited save is not. Backups + `--restore` make this cheap to test.
3. **mods-enabled-by-default unknown.** Expected from evidence (no mod state
   is stored in any save), but if wrong the fix is one toggle in the mod menu.

## 5. Recommended order for the owner's live test (lowest risk first)

| # | Step | Risk | Time |
|---|---|---|---|
| 1 | `pwsh tools/apply.ps1 -GameDir "<game>" -List` — prints what it *would* copy, writes nothing | none | 1 min |
| 2 | `pwsh tools/build-dist.ps1 -GameDir "<game>" -Clean` — verify `dist\ShotgunKing-Modded\mods\` contains 14 folders; your install unchanged | none (copy only) | 2 min |
| 3 | Launch the copy, open the mod menu, confirm the 14 mods are listed and toggleable, quit | low | 3 min |
| 4 | `pwsh tools/apply.ps1 -GameDir "dist\ShotgunKing-Modded" -GetLog` then send `uploads/game-insights/log.txt` | none | 1 min |
| 5 | 100% save, *after* step 3 has created `save/`: `python tools/make_100pct_save.py --game-dir "dist\ShotgunKing-Modded"` then play and inspect | low, reversible | 3 min |

Step 4 output is still **the** blocker for every gameplay feature (ammo
rework, pickers, cheat panel): the mod needs the real function names and
signatures only the runtime map provides.

## 6. Verdict

Tooling is ready to test: the copy-vs-install model is now explicit, two real
script bugs are fixed, and every claim in the README has a verification state.
Feature work stays correctly blocked on one live run.
